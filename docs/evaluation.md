# 评测方案

## 招聘主流程回归基准

`data/recruitment-benchmark-v1.json` 将用户提供的 3 个岗位、12 位合成候选人固化为招聘主流程回归基准。它只检查强、中、弱候选人的相对档位、硬性条件分组、关键证据状态和身份信息隔离，不设置绝对分数门槛。运行 `npm run benchmark:recruitment` 可对数据库中的最新结果执行检查。

这套基准是行为护栏，不是评分标尺：样本中的候选人整体偏强或偏弱，都不会改变新候选人的评分锚点；基准内容不进入岗位建模 Prompt、检索语料或候选人评分上下文。三个岗位也不是支持范围白名单，真实任务始终根据 HR 输入的任意 JD 动态生成维度、权重和硬性条件建议。

当前数据集 `v1.7.1` 包含 60 条合成 JD—简历—回答案例，覆盖财务 AI 产品经理、AI 产品经理、通用产品经理、后端工程师、数据分析师和电商运营六个岗位方向，以及直接匹配、可迁移经验、证据缺失、履历冲突、夸大表述和安全边界六类场景。证据不足项仍保留该状态，同时使用 0–24 分表示当前材料匹配程度并纳入总分；它不是对候选人真实能力的断言。案例已按统一评分锚点完成 AI 辅助规则复核，但这不等于真实 HR 标注。

`v1.7.1` 延续上一版的盲审题面去重：每个岗位的材料缺失、履历冲突、夸大表述、安全注入和身份信息案例都使用不同的岗位事实，不再只是替换岗位名称。每轮 20 条盲审按 10 种判断模式各抽 2 条，并将六类岗位控制在每类 3～4 条；同一案例 ID 不会重复出现。相同风险模式仍会出现两次，用于检查规则能否跨岗位成立，但不会把它伪装成“稳定性测试”。

这些答案仍是产品设计标注，尚未经过真实 HR 复核，因此看板只展示“当前模型相对设计标注的结果”，不能对外称为线上准确率或 HR 一致率。看板分别统计“AI 辅助复核”和“HR 复核”；HR 保存修改后才计入后者，并保留复核来源与时间。

当前自动指标包括：状态判断准确率、引用准确率、证据覆盖率、无依据结论率、冲突召回率、分数区间命中率、任务耗时、Token 和可选成本估算。每次模型或 Prompt 更新都固定数据集重跑并保留历史。上线门槛优先关注无依据结论率、引用准确率和冲突召回率，而不是单一综合分。

看板使用一套明确标为“首版内部门槛”的发布判断：状态判断准确率≥90%、引用准确率≥95%、证据覆盖率≥90%、无依据结论率≤2%、冲突召回率≥90%、分数区间命中率≥70%。只有全部通过才建议进入小范围试用；这些阈值不是行业标准，后续必须依据真实 HR 标注和风险偏好调整。

## 当前合成基线

2026-09-09 使用数据集 `v1.7.1` 与判断规则 `evidence-judge-v3.0` 完成 60 条全量运行：状态判断准确率 98.3%、引用准确率 100%、证据覆盖率 100%、无依据结论率 0%、冲突召回率 100%、分数区间命中率 90.7%，通过 6/6 项首版内部门槛。`v3.0` 将“证据状态”和“当前材料匹配分”拆开：证据不足仍明确标注为低置信度，但给出 0–24 分暂估分并纳入总分；简历与面试冲突仍不强行计分，必须由 HR 核实。该结果仅反映模型与合成设计标注的一致程度，不代表真实招聘准确率。

2026-09-09 使用去重后的数据集 `v1.6.0` 与判断规则 `evidence-judge-v2.7` 重新完成 60 条全量运行：状态判断准确率、引用准确率、证据覆盖率、冲突召回率和分数区间命中率均为 100%，无依据结论率为 0%，通过 6/6 项首版内部门槛。`v2.7` 重点修正了两类失败：不同业务场景中的真实行动应作为可迁移证据低分评价；纯身份信息必须在进入模型前被排除，不能作为解释性引用。

这仍然只是模型对合成设计标注的拟合结果。全量 100% 不代表真实招聘准确率，也可能说明合成案例边界较清晰；对外材料必须同时披露数据来源、案例数量与尚未完成真实 HR 复核的限制。

2026-09-08 使用数据集 `v1.5.0` 与判断规则 `evidence-judge-v2.6` 完成 60 条全量运行：状态判断准确率 98.3%、引用准确率 100%、证据覆盖率 100%、无依据结论率 0%、冲突召回率 100%、分数区间命中率 95.8%，通过 6/6 项首版内部门槛。

这组结果是已冻结的历史基线，只说明当时规则与 `v1.5.0` 合成设计标注的一致程度，不能表述为真实招聘准确率。`v1.6.0` 延续可迁移经验与跨场景协作的证据规则，完成盲审题面去重，并把纯身份边界样本从模型证据入口排除；升级后需要重新运行模型评测，不能沿用旧版本指标。下一阶段仍需由真实 HR 对样本子集盲审并记录分歧。

身份属性采用两层防护：脱敏后，检索层还会阻止只包含姓名、年龄、籍贯、政治面貌等身份属性而没有岗位证据的片段进入评分模型。包含真实工作行动或岗位相关学历、专业、资格要求的混合片段仍可进入检索，但模型不得使用学校名气等属性评分。

本地开发执行 `npm run dev` 会同时启动 Web、简历评分 Worker 和模型评测 Worker。HR 在“模型评测”页面启动任务后可以离开，后台仍会继续运行。

## 校准工作流

看板会自动对比最近两次已完成运行，并以百分点展示各项指标的变化。模型升级不能只看某一个上涨指标；若引用、冲突识别或无依据结论出现回退，应保留基线并继续分析失败案例。

“需要改进的案例”支持 HR 展开诊断并修订设计标注，包括预期状态、合理分数区间、必须引用/禁止引用的证据，以及修订原因。保存后的标注会记录复核时间，并直接用于下一次运行。没有人工保存的案例仍明确标为设计标注，不计入“已人工复核”。

## 产品负责人盲审

在暂时没有真实 HR 参与时，管理员可以启动一轮 20 条“产品负责人盲审”。系统按场景均衡随机抽题，提交前只返回岗位、当前维度和候选人原文；设计标注、场景标签、AI 状态、AI 分数和理由均不会进入盲审响应，评测页上的模型结果也会暂时隐藏。

每条回答记录判断状态、人工分数、所选原文和理由，并在数据库中自动保存，可离开页面后继续。全部完成并确认提交后，系统才展示状态一致率、引用选择一致率、平均分差和需要复盘的案例，同时并排呈现产品负责人判断、AI 结果与设计标注。该结果必须标记为“产品负责人复核”，不能表述为 HR 专家评测或真实招聘准确率。

盲审答案本身不会自动改变工作台。只有在结果页逐条处理分歧，明确选择“AI 更合理”“我的判断更合理”或提交第三种修订后，该案例的设计标注才会更新，并用于同一数据集下一次模型评测。这个动作不会修改真实招聘任务、候选人历史评分或模型参数；它只是形成一份可追溯的产品负责人标签。旧数据集的盲审继续按原版本展示，避免案例升级后错配答案。

批次进度表示已处理案例数；即使个别模型调用超时或返回非法结构，批次也会正常结束，同时在失败数和案例诊断中单独呈现，避免页面长期停留在“未完成”。

后台 Worker 接单时会用自身实际加载的模型与 Prompt 版本回写运行记录，防止本地热更新或滚动发布期间出现“页面版本已更新、Worker 仍执行旧规则”却被错误记为新版的情况。

## 岗位覆盖

招聘主流程不依赖产品经理模板。真实任务初始不带评分维度，必须先输入岗位名称与 JD，再由模型起草 3–8 项岗位专属初筛维度。招聘负责人可以修改部分维度、重新生成、增删与调整权重，也可以切换为三项空白自定义框架后完全重写。示例任务中的财务 AI 产品经理仅用于演示，不代表产品边界。
