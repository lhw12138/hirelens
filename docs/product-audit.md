# MeritTrace 第一性原理产品审视

## 产品必须创造的价值

招聘问题不是“缺少一个 AI 分数”，而是岗位标准含糊、证据散落、判断难以复核。MeritTrace 的核心产出应当是可核对的判断链：岗位要求 → 候选人原文 → 当前证据状态 → 人工决定。

候选人端解决的是另一个任务：在投递前发现“真实经历没有写清”与“岗位确实需要补足”的差别。它不能成为绕过招聘方的隐性排名工具。

## 当前最重要的不足

1. **尚无真实 HR 校准数据。** 合成评测证明流程能运行，不能证明评分在真实岗位上可靠。上线后首要指标不是用户数，而是 HR 修改率、证据引用有效率、严重漏证据率。
2. **任务边界仍偏宽。** JD 解析、初筛、邀约、面试记录和综合审核都已覆盖，但每一段都需要更强的失败恢复。优先把“上传 20 份简历后稳定得到可复核初筛”做深，再扩张 ATS 功能。
3. **隐私治理还缺运营闭环。** 已有脱敏与数据隔离，但仍需隐私政策、保留期默认值、账号删除、数据导出和模型供应商说明。
4. **成本保护处于试用级。** 候选人端已有单账号每日 5 次、全站每日 100 次上限和并发锁；多实例部署前要换成共享限流，并增加单次 token/费用上限。
5. **账号系统仍是 MVP。** 候选人已可用邮箱和密码直接注册，但尚无邮箱验证、找回密码和异常登录审计，补齐前不宜大规模推广。
6. **品牌完成了界面改名，基础设施仍保留旧标识。** 数据库、容器、镜像仓库沿用 `hirelens`，这是为了避免一次高风险迁移；对外不展示，后续在有回滚方案时单独迁移。

## 下一阶段顺序

- P0：完成服务器数据库迁移、镜像构建和小范围内测；用合成简历验证，不用真实资料冒烟。
- P0：找 2–3 位 HR，用 20–30 份经授权或合成改写的简历做盲审，记录每条引用是否支持结论。
- P1：补账号删除/数据导出、隐私政策、默认保留期、共享限流和费用告警。
- P1：把 HR 对评分与证据的修改沉淀为校准数据，按岗位族观察偏差，不追求单一“准确率”。
- P2：当初筛质量稳定后，再考虑 ATS 集成、多组织、邮箱验证和自适应面试。

## 暂时不做

- 自动录取/淘汰、成功率预测、候选人跨岗位排名。
- 未经候选人确认把自测报告推送给招聘方。
- 用学校、年龄、性别、婚育、籍贯等敏感或代理变量评分。
- 在没有真实验证数据前展示准确率、节省时间或客户案例。
